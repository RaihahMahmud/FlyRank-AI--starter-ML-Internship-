A practical ranking approach for deciding which content pages deserve human review first.

Abstract

Content teams often have more pages to review than they have time to review them. This project asks whether observed search-performance signals can be used to prioritize those pages into a useful review queue. I aggregate the March 2026 FlyRank warehouse data at the client and content-page level and train a Logistic Regression model using impressions, CTR, and average search position. The model is evaluated on an 80/20 client-grouped split, with the click threshold and baseline thresholds learned from the training clients only. On the held-out clients, the model reaches 0.9993 precision, 0.9863 recall, and 0.9927 F1, compared with 0.0000 for all three metrics for the simple rule-based baseline. The result is useful as evidence that the model reproduces the observed click-volume target well, but it should be treated as a prioritization signal rather than evidence that refreshing a page will cause better future search performance.

Research note — prepared as an independent analysis for the FlyRank Machine Learning Internship capstone.

1. Introduction

The decision behind this project is straightforward: if an editor has a large set of pages to review, which ones should be looked at first?

A page can have substantial search visibility but weak CTR, or it can have a different combination of impressions, CTR, and position that makes it worth investigating. Rather than asking the model to make the editorial decision itself, I use it to create a ranked queue. A person can then inspect the pages at the top of that queue and decide what, if anything, should change.

Important framing: this is not a model of Google's ranking algorithm. It is also not a causal study of content refreshes. The model works with observed search-performance data and supports a human review decision.

2. Data

The analysis uses the March 2026 FlyRank internship warehouse release, specifically the fact_content_daily_performance table.

9.84Mdaily records
31reporting dates
55raw clients
176,738modeling records

The raw data contains 9,841,378 daily records across 31 reporting dates and 55 clients. For modeling, I aggregate the data to the client_hash_id + content_hash_id level. The resulting modeling dataset contains 176,738 content-page records across 47 clients.

Signals used

  • gsc_impressions — observed search impressions
  • ctr — clicks divided by impressions
  • gsc_avg_position — observed average search position

Rows missing impressions or clicks were excluded because CTR could not be calculated reliably. Records still missing a required model feature after aggregation were also excluded.

The public version contains no client names, domains, URLs, private search queries, credentials, or raw private exports. Identifiers remain pseudonymous.

3. Methodology

Target

The target is intentionally simple: a page is labeled positive when its aggregated click volume is above the training-set median. This is a proxy for identifying pages with stronger observed click-volume patterns. It is not a direct label for whether a page should be refreshed.

Model

I use Logistic Regression with standardized features. The model produces a score for each held-out page, and pages are ordered from the highest score to the lowest score to form the review queue.

Baseline

The comparison point is a simple rule: flag a page when its impressions are at or above the training-set 75th percentile and its CTR is at or below the training-set 25th percentile.

Validation

The train/test split is grouped by client_hash_id. Eighty percent of the grouped data is used for training and 20% is held out for testing. The split produced 138,310 training rows and 38,428 test rows across 37 and 10 clients respectively, with zero client overlap.

Leakage checks

  • No future-window features are used.
  • The click threshold is calculated from training data only.
  • The baseline thresholds are calculated from training data only.
  • Test clients are completely separate from training clients.

4. Results

The model and baseline are evaluated on exactly the same held-out client test set.

MethodPrecisionRecallF1
Logistic Regression0.99930.98630.9927
Rule-based baseline0.00000.00000.0000

The Logistic Regression model identifies most positive cases under the observed click-volume target, while the baseline identifies none on this particular test split. That is a strong difference on this evaluation, but it should be interpreted narrowly: the model is reproducing the chosen target much better than this particular baseline. It does not establish that Logistic Regression is better than every possible rule-based method.

What I would not conclude: a high model score does not mean that a page will gain traffic after a refresh. The experiment does not contain a controlled before/after intervention, so that causal conclusion is not supported.

How an editor can use it

  1. Start with the highest-ranked pages. These are the pages the model considers most consistent with the positive target.
  2. Look for CTR opportunities. For pages with strong impressions and relatively low CTR, inspect the title, snippet, search intent, and content match.
  3. Protect visibility. Pages with high impressions are worth reviewing because they already receive meaningful search exposure.
  4. Use human judgment. Check relevance, intent, recent changes, content quality, and data quality before making a change.

The queue is therefore a starting point for editorial work, not an automatic publishing system.

6. Limitations

  • The target is a click-volume proxy, not a direct measure of refresh opportunity.
  • The analysis uses historical observational data and does not prove that a refresh causes better future performance.
  • The held-out clients improve the validation design, but the evaluation is still based on historical data.
  • The baseline is only one simple rule and performed poorly on this particular split.
  • Only three search-performance features are used; content and engagement context could add useful information.
  • Model scores are used for ordering the queue and should not be read as calibrated probabilities.
